REVIEW FINDINGS
1. Ctrl+Tab was classified as editor Tab and could silently omit a browser
   transition. Generic selection also used the destination window title before
   selecting the tab, so playback could not reliably find an inactive page.
2. Edge UIA tab names contain changing memory-usage suffixes. Exact full-name
   persistence is unstable. The first live capture exposed this and preserved
   its partial draft rather than claiming success.
3. Shared desktop input interfered with the second live capture. Its draft has
   unrelated window/scroll actions and MUST NOT be replayed as an acceptance
   workflow. No text contents were captured in those actions. The candidate is
   stopped in draft review; the recording-name box also received unrelated
   typing. Further desktop control was stopped to avoid interfering with it.

IMPLEMENTED CANDIDATE (phase3-build-5)
- Explicit browser_tab v2 / edge.tab.v2 action with exact source window context
  and a named destination page. Restricted to Edge TabItem with empty scope and
  no arbitrary payload. Existing saved tasks are not transformed.
- Ctrl+Tab and Ctrl+PageUp/PageDown are separate from editor Tab. Clicks on
  browser chrome TabItems use the same semantic action.
- Capture requires an already-recorded action in the source window, selected
  browser tab, matching parsed Edge window title and unique visible top-level
  document. Unsupported/uncertain observations stop and preserve the draft.
- Browser chrome ancestry is bounded and excludes controls inside documents.
- Known English memory-usage decoration may vary; page prefixes, unknown
  decorations and duplicate matching tabs do not supply an identity.
- Replay requires the exact source window/application and independently
  verifies its starting document, selects the unique destination through UIA,
  then verifies selected tab and active document. It has cancellation, focus
  checks, timeout and no repeated selection after an uncertain result.
- Action log describes the new step as Switch browser tab.
