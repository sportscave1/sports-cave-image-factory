Email V2.2 — local implementation and verification, 27 September 2026

1. **Live method:** bounded polling. No permanent IMAP IDLE worker or socket was introduced.

2. **Why:** the existing OS already has a browser notification scheduler and a Streamlit Email fragment. Reusing these avoids a long-lived socket tied to a rerunning session. Axigen documents IMAP IDLE support, but the specific VentraIP server's capabilities were not probed because this task prohibits real-mailbox access. See [Axigen's supported standards](https://www.axigen.com/documentation/rfcs-other-standards-p45253621).

3. **Interval and recovery:** the existing shared scheduler now checks Email every 30 seconds while the app is active. Orders retains its 60-second request cadence; a JavaScript execution test verifies both. The Email component and controller coalesce repeated events using a 25-second guard. Hidden Email documents and conflicting operations skip a tick. Browser throttling, slow network operations, or an open menu can delay the next check. Read failures receive the existing single reconnect attempt; subsequent retries wait for the next heartbeat. No automatic replay of mailbox writes was added.

4. **Commands:** the visible folder uses a fresh authenticated connection, read-only SELECT/EXAMINE, `STATUS (UNSEEN MESSAGES UIDNEXT UIDVALIDITY)`, and `UID FETCH <loaded UIDs> (UID FLAGS)`. The flags request detects changes made by Thunderbird without requiring CONDSTORE. A higher UIDNEXT adds a bounded `UID SEARCH UID low:high`, followed by header-only fetches for new matching UIDs. Existing search constraints remain scoped to the folder/new UID range. Changed UIDVALIDITY replaces the bounded header view safely. The initial SELECT response supplies the arrival baseline, so a sparse search does not repeatedly rescan historical UIDs.

5. **No background content downloads:** unchanged checks have no BODY command. Arrival checks use `BODY.PEEK[HEADER.FIELDS (...)]` exclusively for headers, never body sections, BODYSTRUCTURE, previews, or attachment content. Recovery loading disables previews too. No order loader or Shopify call is used by this path. Normal checks cover up to 1,000 loaded rows plus at most 100 opened thread headers; ordinary initial loading remains 50 messages.

6. **Open marks read:** an intentional row click, expanded message click, or notification deep-link loads the selected message successfully, then explicitly sets `\Seen` through the shared action handler. The body reader still uses PEEK. Only the selected/displayed message is marked; collapsed history is not. Loading headers, polling, resolving history, and generating previews never mark read. A failed body fetch does not mark read; an already-read message does not issue a redundant STORE.

7. **Mark unread:** the same handler removes `\Seen` in IMAP. Local flags and counts update only after the server operation succeeds. Reopening that unread message intentionally marks it read again. Failures leave the last confirmed UI state and show a compact retry message.

8. **Inbox count:** successful actions immediately adjust the known shared unread count, then the next STATUS check reconciles it with mailbox truth. Bulk operations read STATUS after STORE so a newly arriving message is not falsely counted as read. Unknown counts remain unknown.

9. **OS badge and bell:** the existing badge component, header bridge, notification endpoint, and storage are reused. A sibling-iframe trust check now accepts events from the marked OS header; the previous parent-only listener rejected that header's messages. Existing `app_sync_state` cursors, mailbox/UIDVALIDITY/UID identities, transaction locking, and `audit_logs` deduplication remain unchanged. First-run baselining and restart protection remain covered by tests. No new notification system or database table was added.

10. **Message context menu:** right-click a row, use its subtle ellipsis, or use the reading toolbar ellipsis. Actions are Open, Reply, Reply all, Forward, Mark read/unread, Flag/unflag, Archive, Move to, Copy to, Junk, and Trash. The row targets its latest message; reading-pane actions target the selected individual message. Right-click alone does not open or mark the message. Menus stay inside the component viewport, close on outside click/Esc/action, and support Up/Down/Enter. Attachment downloads remain in the existing detail view; no Print or Save As feature was added.

11. **Folder menu:** right-click or ellipsis offers Refresh, Search messages, and Mark folder read. Search focuses the existing scoped search field; in the current folder it does not perform another mailbox load. Refresh reloads that folder's header view while retaining discovered folders and opened body caches.

12. **Mark folder read:** a compact Cancel/Mark read confirmation precedes `UID SEARCH UNSEEN`, then `UID STORE +FLAGS.SILENT (\Seen)` in batches of 500, followed by STATUS UNSEEN. No message content is fetched. Only confirmed affected UIDs update locally. No destructive folder operations or EXPUNGE were added.

13. **Move/Copy:** destinations come from discovered selectable folders, excluding the source folder. Toolbar, row menus, and folder commands use the same controller/provider layer. Copy uses UID COPY and preserves the original. Move/Archive/Trash/Junk reuse the existing capability-aware UID MOVE implementation and special-use mapping. The existing safe copy-only fallback remains when MOVE is unavailable; its explanatory notice is retained. No unsafe delete/EXPUNGE fallback was introduced.

14. **Shared mailbox:** Nathan and Maria use the same real Seen, Flagged, and folder state. Another client's changes appear on the next active-folder check. Bell-handled state remains separate from mailbox flags; an explicit click-through now opens/reads the target according to the new V2.2 behavior. There is no per-user fake mailbox state.

15. **Connections/cache:** polling, notifications, reads, and actions own separate bounded connections and log out cleanly. Sockets are never placed in session caches. Opened bodies remain in the existing bounded display cache. Flag-only changes preserve resolved thread membership; arrivals/removals invalidate membership without reparsing opened bodies. Selection, an unfinished composer, current query, and folder/list scroll positions survive live updates. An opened notification target outside the latest header page remains readable. Heartbeats do not consume the session's action-deduplication ledger indefinitely.

16. **Performance:** 50 fixture polls over 50 loaded UIDs averaged **14.217 ms**, maximum **17.963 ms**. Each used LOGIN, read-only SELECT, STATUS, flags-only UID FETCH, and LOGOUT; zero body/attachment fetches. Reopening a cached message measured **0.02 ms** controller time plus **0.13 ms** model preparation, with no provider call, HTML conversion, or order query. A simulated 240 ms cold body read measured 241.65 ms and one explicit flag operation. These are local fixture measurements, not claims about VentraIP network latency. Reproduce with `python -m tests.profile_support_email_live`.
