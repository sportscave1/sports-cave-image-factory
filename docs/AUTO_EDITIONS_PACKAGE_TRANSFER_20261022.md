## Focused local fix

- Retain the legacy **256 MiB per-request** ceiling. Before writing another ZIP
  or transferring, calculate its exact STORED wire size and report size + budget.
- Reuse the existing durable PostgreSQL/Dropbox **8 MiB chunk** protocol for
  explicitly negotiated large packages, up to **1 GiB wire / expanded disk**.
  No new primary service, queue architecture or whole-package memory buffer.
- Keep the existing **160 MiB per-asset** and **95 MP worker** limits. Check
  temporary disk space before packaging, download and expansion with a 256 MiB
  reserve. Temporary worker disk shortages retain the durable package for retry.
- Require both existing resumable production acceptance and the new
  `provider-postgres-retention-large-v2` acceptance scope before advertising or
  admitting large customer packets. Old servers/acceptance remain limited to
  256 MiB; retained sessions never fall back to replay through legacy HTTP.
- Existing chunk hashes, durable offsets, provider content receipt, complete
  SHA-256, source/lease/generation binding, asset checksums, ICC and independent
  image proofs remain in force. Retry/finalize reuse the same session identity.
- On a normal design retry, reuse compatible finished exports from the failed
  job under the fresh lease, recomputing proofs. Do not rerun Photoshop merely
  because a compatible package was never finalized. Preserve old journals/files;
  incompatible source, generation, reset or target policy cannot reuse them.
- Add a specific Companion package diagnostic and actionable budget errors.
- Extend the existing isolated, administrator/host/run-scoped acceptance harness
  with a bounded synthetic packet above 256 MiB. New Companion acceptance uses
  that fixture when advertised; a fresh run is required for large-v2 evidence.
  The result records packet bytes and acceptance scope. Synthetic ZIP preamble
  is transport load only and never evidence of artwork compression/quality.
