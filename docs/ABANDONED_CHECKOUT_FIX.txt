SPORTS CAVE OS - ABANDONED CHECKOUT RELIABILITY FIX
Reviewed locally 6 October 2026 (Australia/Sydney)

1. ROOT CAUSES
Names: the table explicitly generated "Customer <numeric id>". The normal
Shopify list/detail queries requested only customer IDs. The identity refresh
required both a signed webhook-key match and a customer ID, excluding guests
and legitimate Admin objects that had no matching signed checkout record.

Misleading Recovered rows: the page selected the general checkout/order ledger,
including order-only records. Read-only production inspection found 39 recovered
rows, all with order IDs, plus 3 open rows; none had an Admin abandoned-checkout
ID or a cached name. These were not evidence of 39 recovered abandoned carts.
A second defect classified a missing Shopify checkout response as recovered and
persisted that classification. Missing objects now hold/retry verification.
Recovery display uses order/completion evidence; flow state and queued mail do
not prove conversion. Accepted sends require a provider receipt.

Historical entry: refresh-only identity guards, a required webhook-key/customer
match, and an invalid equality check between Admin abandonment creation time and
original webhook checkout creation time prevented legitimate manual entry.
Manual entry now resolves the exact Admin object, persists its mirror, checks
consent/suppression/native unsubscribe safety, and freezes the published flow.

New entry: production recovery URLs use /checkouts/ac/<token>/recover. The old
parser supported only cn and unprefixed paths, so it returned no usable key.
Admin recovery tokens also differ from original signed webhook checkout tokens;
requiring those identities to match excluded the real Admin object. The polling
loop additionally reused its state-key variable for checkout keys, corrupting
pagination progress. Original creation-date filtering could exclude checkouts
still active after activation. Polling now uses updated_at with a persistent
future-activity boundary and a separate pagination state key.

5. UI RESULT
Compact Shopify-style table: checkbox, Checkout, Created (UTC), Customer name,
Region, Recovery status. The three subtle pills are Not sent (red), Not recovered
(orange), Recovered (green). Names use verified customer names, address names,
email, then Guest. Numeric IDs never serve as customer names. Shopify's own
checkout name is preferred. Search matches checkout, customer name and email.
Checkbox selection supports multiple rows and 50-row pagination. Refresh and
Add to flow are adjacent above the table. All specified bottom clutter is gone
from this operational view; general flow analytics remain in their own path.
Click a checkout reference to open details; close it to return to the clean table.

6. HISTORICAL ENROLMENT / REPAIR
Select the desired row checkboxes and click Add to flow. It is disabled with no
visible selection and processes only selected rows. Results explain Added to
flow, Already in flow, Recovered, Missing/Invalid email, Suppressed, Unsubscribed,
Not eligible or Error. The table refreshes after the operation. Enrolment is
persistent and idempotent. First due time is max(manual enrolment time,
last activity + published abandonment wait + first-email delay); subsequent
steps retain the existing published rules.
Refresh checkout details is a secondary resumable repair, reporting Updated,
Unchanged and Failed. It refreshes identity/recovery facts without enrolment,
queue creation or sending, preserves receipts and genuine recovery evidence,
and never deletes history. Normal worker sync provides identities automatically.
Missing-account guests can resolve a verified, unique email profile; absent
verified consent or unsubscribe authority is explicitly blocked, never bypassed.
