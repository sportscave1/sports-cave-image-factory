## Restart scheduling defect and local repair

The index worker loses a PostgreSQL lease during overlap with another owner, restores cached mail, then unconditionally sleeps the full60-second normal polling interval. A released lease can consequently remain unused for almost another minute. A deterministic regression running the real worker loop with competing claim outcomes failed on released source (wait60s), then passed after repair (wait5s). This establishes a scheduling defect, not proof that every second of the historical134-second interval had that cause.

Read-only historical Render logs show old kh9cq still completing index sync at22:22:56 UTC and performing provider operations at22:25:02–04, despite the replacement becoming live22:23:01. Official Render deploy documentation confirms overlapping old/new instances and a60-second drain before SIGTERM. No historical lease-denial log was available to assign the entire134s to one specific cause. IMAP connect/auth/select in those logs took approximately0.7s/0.2–0.5s/0.2s; they do not indicate a134s network/authentication stall.

`support_email_reads.py` now retries lease contention after5s, backing off5/10/20/40/60s for persistent followers, resetting after takeover. Provider/authentication backoff takes precedence. It never fetches provider mail while a different worker owns the lease. Normal successful polling stays60s. Safe lease-busy logging includes only retry seconds. No outbox/send code changes.
