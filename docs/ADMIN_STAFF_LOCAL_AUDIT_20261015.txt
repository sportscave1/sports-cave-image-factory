Prodigi investigation
---------------------
No demonstrable new loading defect was found, so no Prodigi source was changed.
Its initial dispatch log submits one asynchronous latest-50 read, skips Shopify
and the full order snapshot, and does not download artwork. Search is submitted
in a form. The loading fragment polls once per second and stops via a full rerun
when the future resolves. The UI has an eight-second timeout and an explicit
Retry button; it retains prior rows on failure. The DB read owns its connection,
has a six-second query/pool watchdog after connection establishment, and retries
once only for a stale connection. Network connection establishment and cancellation
can extend the database task beyond the UI deadline; the UI deadline is not a
guarantee that a running thread has stopped. No unrelated DB policy was changed.

100 repeated pending-load checks submitted exactly one read (~0.59 ms harness
overhead). A synthetic timeout produced an error, preserved prior display data,
did not automatically resubmit, and recovered on explicit retry. With the DB
deliberately held pending, the real Streamlit page shell rendered in ~2259 ms
on cold initialization and ~9 ms warmed. Both role predicates allowed the same
fulfilment renderer. These are test-harness timings, not an admin/staff speed
comparison or the VA's network timings. Both runs requested one 50-row read and
zero asset downloads. No staff-specific extra query/Photoshop path was found.
