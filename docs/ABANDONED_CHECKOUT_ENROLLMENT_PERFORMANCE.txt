Abandoned checkout Add to flow: performance and UX implementation
2026-10-06. Local implementation only; no commit, push or deployment.

CONFIRMED BOTTLENECK
The previous modal iterated selected rows synchronously, calling add_to_flow
serially and publishing results only after the entire loop. Each eligible row
loaded the automation/capability state, fetched a fresh Shopify checkout, wrote
its mirror, read the checkout and existing membership, fetched a fresh customer
or guest-email profile, checked suppression/consent/unsubscribe, then entered the
existing locked enrollment transaction. That transaction rechecks publication,
capability, checkout, inactivity, rules, deduplication and re-entry. The modal
then invalidated/reloaded the entire checkout list. It did NOT wait for email
delivery: enrollment/scheduling, external validation and DB round trips blocked
the UI. Unselected rows were not enrolled by the old path.

Measured against fabricated checkouts and disposable loopback PostgreSQL, with
60ms controlled latency per fresh checkout/customer lookup and the existing
two-request Shopify semaphore:
  Old 12-row serial path: 1.941s, 24 fresh external lookups, 408 SQL calls
    including BEGIN/COMMIT, 108 committed transactions.
  New durable batch acknowledgement: 0.006s, four SQL statements, one commit,
    zero external calls. Validation/enrollment completion: 0.956s.
These establish the serial/round-trip bottleneck and bounded concurrency gain;
they are NOT measured production latencies or a production SLA.

OLD PATH
Button -> selected rows -> serial fresh checks/mirror writes/locked enrollments
-> wait for every row -> one results dataframe -> full checkout-list reload
-> existing background worker creates due email jobs and handles delivery.

NEW PATH
Button -> immediate per-row Adding acknowledgement -> asynchronous batch save
of ONLY selected keys to private crm_runtime_state -> existing crm_worker
claims durable requests -> bounded independent fresh validations -> unchanged
locked enrollment + frozen schedule -> per-row committed result -> targeted
UI schedule/status patch. The existing runtime later creates/processes the
same email queue and performs the same final sending safety checks.

WHAT CHANGED
- Batch automation, selected mirror/membership and suppression reads plus one
  UPSERT for all selected requests: four statements in one transaction.
- No Shopify lookup during request acknowledgement. Persisted positive blocks
  and existing memberships return immediately without expensive external work.
- Four independent enrollment tasks in the existing worker process. Shopify's
  existing shared two-request semaphore, cost limit, retries and timeouts stay
  unchanged. One slow checkout occupies one slot, not the entire batch.
- Overlapping identical customer/guest-profile lookups coalesce in flight.
  There is no cross-request consent cache or stale consent reuse.
- Individual enrollment transactions remain separate to preserve locking,
  fail-closed checks and partial success. No safety check was deleted.
- One targeted status/schedule read per active polling batch (2-second UI
  refresh; no Shopify calls), followed by one cache patch pass. No full-table
  reload on each completion. Normal idle refresh remains 30 seconds.
- Worker polls requests every 5 seconds idle / 2 seconds busy, independently
  from the existing email cycle. First pickup can therefore take up to 5s.
- Ten-minute row leases and owner-fenced results recover after restart. The
  existing enrollment deduplication also covers a crash after enrollment commit
  but before request acknowledgement. Retry history keeps safe error codes.
- The browser receives only state/result labels, not private request history,
  actor details or exception text. Pending/failed requests restore on reopening.
  Completed labels remain in the current session and do not clutter a new one.

WHAT REMAINS INHERENTLY SLOW
Fresh Shopify recovery/customer/guest-consent verification is still required
because the display mirror does not establish fresh consent or non-recovery.
Provider latency/throttling and database round trips can exceed one second.
All of that work now occurs outside the UI thread, with individual results.
No provider send occurs in request acceptance or enrollment processing.

PER-ROW UX
Under the checkout reference, without adding another table column/panel:
  Adding… (request saving/queued, pulsing dot)
  Checking eligibility… (leased worker processing, pulsing dot)
  Added to flow
  Already in flow
  Recovered
  Unsubscribed
  Suppressed
  Missing email
  Invalid email
  Not eligible
  Flow is not live
  Not eligible: Shopify identity unavailable
  Checkout still inside abandonment wait period
  Failed — Shopify unavailable / identity changed / persistence error /
    verification unavailable / request unavailable (with Retry action)
Reduced-motion preference disables the pulse. Status text uses role=status.
Only busy selected rows are excluded from another submission; search, selection,
details, scrolling and unrelated eligible rows remain usable. Retry is explicit,
row-scoped and idempotent. Time to send updates from persisted next_due_at and
frozen steps on the next progress response; its timing/display rules are unchanged.

PERSISTENCE AND DEPLOYMENT
No schema migration, new email queue, new service or environment flag.
Requests reuse the existing server-only, RLS-enabled crm_runtime_state table
under checkout-enroll:<automation-id>:<checkout-key>. Primary-key UPSERT prevents
duplicate active requests; claims use row locks/SKIP LOCKED and lease ownership.
Deploy the web application and the existing CRM worker with this version so the
worker consumes requests. Existing sports_cave_worker.py already runs crm_worker.py.
No Render topology or configuration was changed. No historical scan creates requests.
