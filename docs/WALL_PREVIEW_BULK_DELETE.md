# Wall Preview Inbox bulk deletion

Implemented in the existing Social Media inbox. Ready for deployment after the normal release process; no production deployment or customer-file deletion was performed during development.

## Interaction

- Each card has a 44px checkbox target and a `#D4A54C` selected outline.
- **Select Visible** selects the current filtered page (up to 24 previews). It does not claim to select other pages.
- Selection uses preview IDs, stays entirely inside the existing JavaScript component, and triggers no server requests or image downloads. Changing filters/pages clears selection; refreshing prunes unavailable IDs.
- Delete Selected freezes the selected IDs, opens an explicit count confirmation, removes repeat-submit controls while running, reports progress, and refreshes the grid without browser navigation.
- Individual deletion uses the same service. Failed records are reported individually and retained for retry. A batch-start failure restores confirmation controls.

## Backend and recovery

`POST /api/wall-previews/inbox/bulk-delete` requires an active admin cookie, same-origin intent, `X-Wall-Preview-Action: delete`, and JSON containing `confirmed: true` plus 1–24 UUID `preview_ids`. The existing Streamlit admin interface invokes the same server-only service directly. Credentials never reach the card component.

The service commits a deletion marker before storage changes and commits resolved Dropbox IDs/revisions before deleting. Row locks fence archive/customer workers and storefront updates. Queued email deliveries are suppressed; an email already being delivered produces a retryable failure instead of racing that delivery. Cross-process advisory locking protects shared-file ownership checks. Retries tolerate missing files and resume after a provider success followed by a database failure.

Successful cleanup removes events, job payloads, contact details, share links, order associations, product metadata, and storage references. A minimal private ledger tombstone retains deduplication identities and deletion audit information so stale submissions cannot recreate deleted previews. Legacy deduplication retains an email hash, not the original email. This is intentionally not a physical deletion of the ledger row.

## Dropbox behavior

The inspected implementation archives one composite image per capture. Original room photographs are not separately archived; card thumbnails are generated by Dropbox. Pending composite bytes are held in the archive-job row and are removed with that job.

The existing authenticated team-space client resolves the recorded file and known worker relocation destination. It checks file type, root, ownership, stable Dropbox ID, and revision before deletion. It never recursively lists or deletes folders. Files referenced by another undeleted preview are preserved. Unverifiable ownership fails closed and requires investigation.

Each batch uses bounded sequential file-ID deletion rather than an asynchronous Dropbox batch job, preserving per-preview recovery and shared-file ordering. SDK retry counts are bounded; rate-limit backoff stops further provider requests for the remainder of the cooldown. Missing files succeed, while authentication, rate-limit, and other storage errors remain visible.

Deletion uses Dropbox's standard delete API. Sports Cave OS provides no undo; Dropbox's own retention/recovery policy can still apply. This is not a provider-level permanent purge.

## Configuration

No new packages, environment variables, database migrations, services, or frontend libraries. Uses the existing private database connection and Dropbox team-root authentication with metadata-read and file-write access. Live provider permissions were not exercised by destructive tests; ownership or permission failures are reported safely per record.
